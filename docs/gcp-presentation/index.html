📍 Slide 1 of 7 • Vision & Concept

Homaatri — Agent-First WhatsApp Platform

Connecting Customers, Home-Cook Chefs, and Delivery Riders via plain WhatsApp text.

🧠

"The AI is the Runtime"

A single tool-calling Manager Agent handles all inbound WhatsApp messages across all 3 roles. The backend acts as its deterministic tool belt (~30 tools).

📱

3-Role WhatsApp Simulation

Side-by-side real-time 3-phone web simulator (Customer, Chef, Rider) powered by Server-Sent Events (SSE) at http://localhost:8000.

⚡

Meta 3-Second Webhook SLA

Inbound webhooks are HMAC verified and immediately ACKed (200 OK within <50ms) using FastAPI BackgroundTask workers.

Directory & Module Structure Breakdown

Clear separation of concerns across core layers, database schemas, services, and webhooks.

app/core & app/db

• core/config.py: Settings & env vars.
• core/security.py: Meta & Razorpay HMAC verification.

• models/entities.py: SQLAlchemy models (Users, Chefs, Drivers, Orders, Payments, Vector RAG memory).
• models/enums.py: Domain enums (OrderStatus, PaymentStatus, UserRole).

app/services

• agent.py: LLM tool-calling dispatch loop.
• context.py: Context Assembler (RAG + state).
• policy.py: Action guardrails & preconditions.
• conversation.py: Orchestrator & cross-role relay.
• routing.py: Greedy TSP multi-stop navigation.

🔄 Slide 4 of 7 • API Lifecycle

Minute Inbound Message Lifecycle Execution

Step-by-step path from Meta WhatsApp webhook to LLM tool execution and SSE broadcast.

STEP 1 Inbound POST Webhook: Meta Cloud API posts JSON payload to /webhook/whatsapp containing customer phone & message text.
STEP 2 Security Verification: app/core/security.py verifies X-Hub-Signature-256 HMAC token.
STEP 3 Immediate SLA ACK: FastAPI returns HTTP 200 OK in <30ms and dispatches processing to BackgroundTask.
STEP 4 Orchestration & Context Assembly: app/services/conversation.py fetches user profile, active order, and builds prompt containing Policy Rules + Live Order State + Transcript + pgvector RAG Memory + Rolling Summary.
STEP 5 Policy Guardrail Check: app/services/policy.py evaluates valid state transitions (e.g. preventing food cancellation after cooking starts).
STEP 6 LLM Tool Calling Execution: LLMClient invokes Gemini 2.0 Flash (or fallback Gemini 1.5 Flash). The LLM calls relevant tools (e.g. place_order, add_items, start_cooking).
STEP 7 DB Transaction & Cross-Role Relays: Database updates are committed within an async transaction; notifications sent to Chef and Driver WhatsApp.
STEP 8 SSE UI Broadcast: EventBus pushes real-time state snapshots to the 3-phone simulator frontend.
💳 Slide 5 of 7 • Payments & Top-Ups

Payment Architecture & Mid-Cooking Top-Ups

System-authored amounts, itemized text bills post-payment, and incremental add-on charges.

🔒

Initial Order Payment

• Pay Screen: Displays exact amount only (never hallucinated by LLM).
• Itemized Bill: WhatsApp text bill sent after payment confirmation.
• Webhook Verification: Idempotent Razorpay / Demo webhook updates order to CONFIRMED and alerts chef.

➕

Mid-Cooking Additions & Top-Ups

• Customer requests extra dish mid-order.
• Chef receives ⚠️ Change Request trigger & taps accept.
• System generates top-up payment link for only the delta balance due (total - amount_paid).
• After top-up payment, chef receives updated total summary.

🗺️ Slide 6 of 7 • Logistics Subsystem

Driver Routing & TSP Optimization Engine

Greedy Traveling Salesperson Problem (TSP) + Google Maps multi-destination dispatch.

📍

Greedy TSP Path Optimization

• When order is READY_FOR_PICKUP, app/services/routing.py aggregates drop-off coordinates.
• Runs a Greedy TSP solver calculating optimal multi-stop delivery sequences from kitchen to customer pins.

🔗

Google Maps Dispatch Link

• Formats optimized route into a native Google Maps link:
https://www.google.com/maps/dir/Kitchen_Coords/Cust1_Coords/Cust2_Coords
• Driver receives turn-by-turn navigation link directly on WhatsApp.
