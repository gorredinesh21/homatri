Turning the bot into a restaurant manager — architecture, QA & a path to your own model

How to make the AI reliably act as customer-support + waiter + operations manager across the customer, chef and rider; a full QA scenario catalog to test it; and a grounded exploration of hosting / fine-tuning your own small model on AWS.

Prepared for Dinesh · Homaatri · July 2026 · branch aws-bedrock (Amazon Bedrock Nova live)

1 The vision: one AI, three people to keep happy

Today the bot reacts message-by-message. The goal is an AI that behaves like the manager / maître d' of the kitchen: it owns each order end-to-end and is simultaneously accountable to three parties whose interests sometimes conflict.

🧑‍🍳Customer advocate

Gets the customer exactly what they want — takes the order, answers questions, handles "add 2 more rotis", time/address changes, and keeps them informed at every step.

👩‍🍳Chef protector

Shields the kitchen from chaos: only forwards a change if it's still feasible (not already cooked/packed), batches requests, and never lets a customer edit an order the chef can't honour.

🛵Rider coordinator

Keeps delivery smooth: routes, drop-off location, time changes while en route, and only bothers the rider when a change actually affects them.

The hard part is that these three want different things. A customer's "add a dal fry" is trivial before cooking, awkward during, and impossible after pickup. The manager AI's job is to know where the order is in its lifecycle and mediate accordingly — that is exactly the judgement that needs strong context and clear policy.

The core principleThe AI is not three separate chatbots. It is one operator with one shared, authoritative picture of the order, talking to three people about the same thing.

2 Why the AI "loses context" right now

An honest diagnosis of the current build. None of these are bugs exactly — they're design gaps that show up as forgetfulness and inconsistent decisions.

Bottom lineContext isn't "on" or "off" — it's assembled every turn. The bot forgets because we aren't reliably feeding it (a) the authoritative order state, (b) the recent transcript, and (c) the rules — every single message, in a structured form a small model can actually use.

3 Target architecture: the Manager Agent

A single stateful agent per order, wrapped in deterministic guardrails, with three tiers of memory and a policy layer. The LLM handles language and judgement; the state machine guarantees the order can never be corrupted.

The three tiers of memory (this is the real fix)

  1. Working state (always injected): the full order object — items, quantities, status, totals, delivery time/address, rider, pending changes — rendered as compact structured text on every turn. Never rely on the model to "remember" this.
  2. Short-term transcript: the last 6–10 messages of this conversation, verbatim, so the model has the immediate thread (fixes "forgot what I just said").
  3. Long-term trio memory: the (customer, chef, driver) pgvector store you already built — surfaces durable facts ("this customer always wants less spicy", "gate code 4321") retrieved by relevance.

Policy layer — encode the judgement, don't improvise it

The manager's decisions should be rules keyed off the lifecycle state, given to the model as explicit policy and enforced by tool pre-conditions:

Order stateAdd / change food?Change time?Change address?Cancel?
Awaiting payment✅ edit freely, re-issue link✅✅✅ free
Confirmed (not started)✅ add, notify chef✅✅✅ (pre-cook)
Preparing⚠️ only if feasible → chef approves; charge top-up✅✅⚠️ partial
Ready / not picked up⚠️ "can we still add 2 rotis?" → ask chef✅✅⚠️
Out for delivery❌ too late⚠️ inform rider⚠️ rider approves❌
Delivered❌ (new order)❌❌❌

This table is the manager's brain. It goes into the system prompt as policy, and each tool (add_item, change_time…) checks it as a pre-condition so the model literally cannot do the wrong thing even if it tries.

Concrete changes to the current code

  • Add a ConversationState table/row per order: summary (rolling), open_threads (e.g. "customer asked to add dal fry — awaiting chef"), updated after each turn by a cheap summariser call.
  • Rewrite the context assembler so every agent prompt = policy + order state + last N turns + retrieved memory + open threads. One function, one shape, every role.
  • Add the top-up payment + feasibility check tools (partly started on this branch) so "add 2 rotis after cooking" has a real path: chef-approve → price delta → top-up link.
  • Promote the manager model to Nova Pro (or Claude 3.5 Haiku/Sonnet on Bedrock) for the reasoning-heavy turns; keep Nova Lite/Micro for parsing & summarising.

5 How we test it (QA strategy)

You can't unit-test "did it behave like a good manager" with plain asserts. We use three layers.

1 · Deterministic e2e

The pytest suite (23 passing) drives the real HTTP + lifecycle with the LLM off, proving state transitions, guardrails, payment signatures, memory isolation. Fast, runs on every commit.

2 · LLM behavioural eval

Each scenario becomes a scripted conversation run against the live model. An LLM-as-judge scores the transcript against a rubric ("did it refuse the post-pickup add-on?", "did it get quantities right?"). Produces a scorecard per model/prompt.

3 · Regression & canary

Golden transcripts + judge scores are stored. A model swap or prompt edit re-runs them; a drop in score blocks the change. New models canary on a fraction of traffic first.

Tooling fit

The eval harness is a thin script over the existing /api/sim/* endpoints (already how we drive the simulator). Judge = a cheap Bedrock model with a strict rubric prompt. This gives you a repeatable "manager quality score" you can track release over release — and it's the same harness you'd use to prove a fine-tuned model is actually better before promoting it (§7).

Which small model?

For a tool-calling maître d', pick a model with solid function-calling: Llama 3.1 8B Instruct (proven tool-calling, huge ecosystem), Qwen2.5-7B, or Ministral-8B. All run on a single 24 GB GPU with vLLM and expose an OpenAI-compatible endpoint — meaning zero application code change: just repoint the base URL. (Or stay on Bedrock Nova / Claude and skip servers entirely.)

Key insightYour app already speaks the OpenAI Chat Completions shape. Any of these (vLLM, SageMaker, Bedrock via a thin adapter — which the aws-bedrock branch already has) drops in behind the same interface. The provider is a config choice, not a rewrite.

7 A model that learns from your chats (fine-tuning & "self-improving")

You want a model that improves from customer / chef / rider chat history — ideally "updating itself". Here's the realistic, safe version of that, and how AWS does it.

The data you're sitting on

Every conversation is a labelled training example: the transcript + the outcome (order completed? change handled? customer happy? chef annoyed?). That outcome signal is gold — it's what turns raw logs into a reward.

Two ways to fine-tune on AWS

Bedrock fine-tuning (Nova)

Managed SFT (supervised) and RFT (reinforcement) for Nova, plus distillation. Upload JSONL of good transcripts; Bedrock trains; the custom model serves at the same per-token price as base. AWS reports Nova Micro going 41% → 97% on an intent task after fine-tuning. Lowest effort.

SageMaker + LoRA/QLoRA

For an open model (Llama 3.x): JumpStart fine-tunes with PEFT/LoRA — trains <1% of parameters, cheap and fast, then deploys to an endpoint. Full control over the base model & data. More MLOps to own.

What "self-updating" really means (and the honest caveats)

True online learning (the model rewrites its own weights live from each chat) is not what you want — it's unstable, unsafe, and un-auditable. The production pattern is a continuous improvement loop with a human gate:

1 Collectchat logs + outcomes
2 CuratePII-scrub, label, filter to good cases
3 TrainSFT/LoRA/RFT job
4 Eval§5 judge scorecard
5 Gatepromote only if better
6 Canarysmall % traffic → full
  • Human/eval gate is non-negotiable — a new model ships only if it beats the current one on the QA scorecard. This prevents the model getting worse from noisy data.
  • Feedback loops & drift: training on your own bot's outputs degrades quality over time; mix in fresh human-verified data and hold out a clean eval set.
  • Catastrophic forgetting: keep general instruction data in the mix so it doesn't over-fit to only your transcripts.
  • PII & consent: phone numbers, addresses, names must be scrubbed/tokenised before training; keep training data governed (Unity/S3 with access control).
  • Reinforcement fine-tuning (Bedrock RFT) is the closest to "learns from outcomes" — you define a reward (order completed cleanly, customer satisfied) and it optimises toward it. Up to 20K prompts per job.
Realistic goal: a scheduled retrain (say monthly) on curated, outcome-labelled chats, auto-evaluated and promoted only when it wins. That is a self-improving system — just with a safety gate instead of blind live updates.

9 Recommendation & roadmap

The call

Stay on Amazon Bedrock (you're set up and it's working). Do not self-host or fine-tune yet — first fix the architecture (state + memory + policy) and stand up the eval harness. Those two give you 90% of the "smart manager" behaviour with zero GPU cost. Collect data now; fine-tune later, only once the eval harness can prove it's better.

P1

Now — make the manager reliable (no new infra)

Implement the Context Assembler (§3): always inject order state + last-N turns + policy + trio memory. Add ConversationState rolling summary. Promote the manager turns to Nova Pro. Encode the lifecycle policy table as pre-conditions. → fixes the "loses context" problem directly.
P2

Next — prove it with QA

Build the eval harness (§5): the ~45 scenarios as scripted conversations + LLM-judge scorecard. Wire it into CI. Now every prompt/model change is measured, not guessed.
P3

Later — your own tuned model

Once you have a few thousand real, outcome-labelled conversations: Bedrock SFT on Nova (lowest effort) or LoRA on Llama-3.1-8B via SageMaker. Promote only if it beats the scorecard. Serve on the same interface.
P4

Scale — self-improvement loop & maybe self-host

Scheduled retrain → eval-gate → canary → promote (§7). Move to a SageMaker/EC2 GPU endpoint only when steady volume makes per-token self-hosting cheaper than Bedrock (§8).
One-line summaryThe problem isn't the model or the host — it's that we aren't feeding the model the order state, the recent transcript, and the rules every turn. Fix that first (P1), measure it (P2), then a fine-tuned/self-hosted model is a cost/ownership optimisation you turn on when the numbers say so.
