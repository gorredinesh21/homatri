V1.0 - Production Design

Homaatri System Design Blueprint

A comprehensive, production-ready guide for building a WhatsApp-first, hyper-local home-kitchen food service linking customers, home chefs, and delivery drivers using an automated AI-driven backend.

Operational Model: Housewives cook 2–3 extra meals during their regular family cooking window. Customers request meals via WhatsApp. Homaatri handles billing, allocation, delivery, and notifications. Housewives only cook and package.

Stakeholder Ecosystem

The platform coordinates four primary roles. To achieve zero friction, all daily operational communication is conducted exclusively via WhatsApp.

1. Customer
Orders meals using natural language text/voice or WhatsApp interactive features (Buttons, Catalogs, Flows). Completes payments via instant links.
2. Housewife (Chef)
Receives a consolidated recipe checklist (e.g. "Total: 5 Rotis, 2 Paneer Curry") before cooking windows. Signals cooking milestones using WhatsApp action buttons.
3. Delivery Driver
Receives automated pickup routes, customer details, and delivery instructions. Updates order statuses ("Picked Up", "Delivered") via quick-reply buttons.
4. System Administrator
Oversees orders, monitors driver routes, manages active chef capacity, edits menus, checks payout calculations, and processes manual exceptions.

Architecture & System Flows

The backend acts as an event-driven router. Below is the system flow depicting an order's lifecycle, from a user sending a message on WhatsApp to the dispatching worker.

sequenceDiagram autonumber Customer->>Meta Cloud API: Send WhatsApp order request Meta Cloud API->>Backend Webhook: HTTP POST (Secure payload) Backend Webhook->>Redis/Database Queue: Push processing job Backend Webhook-->>Meta Cloud API: HTTP 200 OK (Keep timeout low) Queue Worker->>LLM API (Gemini/GPT): Parse order JSON & validate items LLM API-->>Queue Worker: Structured JSON (Items, Address, Time) Queue Worker->>Database: Insert Order & Transaction records Queue Worker->>Payment Gateway: Generate link (e.g. Razorpay) Queue Worker->>Customer: Send Payment link via WhatsApp message Customer->>Payment Gateway: Complete transaction Payment Gateway->>Backend Webhook: Payment Success Webhook Backend Webhook->>Database: Set Order to "Confirmed" Backend Webhook->>Chef: Notify order details or compile consolidated list

Design Tip: Webhooks must return an immediate HTTP 200 to WhatsApp within 3 seconds to avoid delivery retries and duplicate runs. Offload the extraction logic (LLM processing and payment generation) to a background worker using a job queue.

Customer Workflow

Customers are presented with a hybrid flow. They can interact by writing message prompts, or they can trigger structured interactive menus.

1. Natural Language Ordering System

When a customer types a message such as "Send me three chapatis and dal by 8 PM", the backend processes it through a strict extraction pipeline:

graph LR RawMsg[WhatsApp Msg] --> Webhook[Verify & Receive] Webhook --> Worker[Queue Worker] Worker --> FetchMenu[Fetch Active Chef Menus] FetchMenu --> LLM[LLM Parse & Match] LLM --> Validation{Validate Schema & Items} Validation -- Validation Success --> DB[Create Order & Pay Link] Validation -- Validation Failed/Ambiguous --> AskClarify[Send WhatsApp clarifying menu/buttons]

Ambiguity Handling: If the user inputs "Curry and Roti", the system fetches today's active menu items. If multiple curries are available (e.g. Paneer Curry and Dal Fry), the LLM flags the payload with an is_ambiguous: true state and lists matching item IDs. The backend interceptor responds with WhatsApp interactive quick-reply buttons allowing the customer to tap the correct item.

2. Interactive Ordering Interface

For a reliable experience, natural language is supplemented by WhatsApp Interactive Messages:

WhatsApp Feature Usage in Homaatri Production Value
WhatsApp Lists (interactive/list) Displaying the current menu options (Up to 10 choices). Prevents typos. Users click "Select Item" to view prices.
Quick Reply Buttons Confirming order summary, choosing pickup windows. High response speed. Limit of 3 buttons per message.
WhatsApp Flows Multi-step form inputs inside WhatsApp (Address + Delivery time). Eliminates external web page loads, native form UI.
WhatsApp Catalogs Browsing standard dish offerings with prices and images. Excellent searchability, native cart experience.

Chef (Housewife) Workflow

The housewife is cooking at home, likely busy and distracted. Regular notifications for individual orders generate confusion. The system is designed to bundle tasks.

1. Consolidated Preparation Summary

Instead of dispatching notifications for every individual order, the scheduler executes a consolidation job at the cutoff threshold of each ordering window (e.g. 11:30 AM for lunch, 6:30 PM for dinner).

graph TD O1[Order 1: 2 Chapatis, 1 Dal] --> Job[Consolidation Engine] O2[Order 2: 3 Chapatis, 1 Paneer] --> Job O3[Order 3: 1 Chapati, 1 Dal] --> Job Job --> Agg[Aggregate: 6 Chapatis, 2 Dals, 1 Paneer] Agg --> WhatsappSender[Format & Dispatch WhatsApp Template] WhatsappSender --> ChefPhone[Housewife Phone (Interactive Checklist)]

2. Real-Time Status Updates

The Chef interacts with the system using button triggers configured on the WhatsApp template notification. Tapping these buttons updates the server state immediately:

  • [Start Prep]: Transition chef status to PREPARING, triggers customer alert: "Chef has started cooking your food!".
  • [Ready for Pickup]: Transitions status to READY_FOR_PICKUP. The backend immediately computes routing and alerts local delivery drivers.
  • [Request Help]: Flags the Admin Dashboard with an alert (e.g., ran out of ingredients, gas issue).

Delivery Driver Workflow & Routing

Delivery drivers operate via WhatsApp templates containing deep links to Google Maps coordinates, client contact details, and pickup cards.

1. Driver Interaction Flow

A driver receives a WhatsApp dispatch message with interactive buttons:

2. Route Optimization Architecture

At Homaatri's operating scale (30–100 orders/day, max 500), complex real-time routing engines (like OSRM clusters or VRP heuristics) are unnecessary overheads. We design a hybrid routing layer:

Backend Allocation Engine
Group orders geographically by customer zip-code and proximity radius. Route matching uses a simple Greedy TSP (Traveling Salesperson Problem) script run inside the Node.js background worker, fetching distance matrices from Google Maps API.
Google Maps API Integration
Use Distance Matrix API once during the driver assignment window (batch-calculated). In driver dispatch messages, format a Google Maps Multi-stop URL (e.g., https://www.google.com/maps/dir/Chef+Loc/Cust1+Loc/Cust2+Loc) so the driver can run native navigation.

Admin Dashboard

A reactive web interface tailored for system administrators. While clients and chefs operate in WhatsApp, the admin relies on a visual dashboard to manage exceptions.

Order Dispatch Control
Real-time status board (Kanban view) showing orders across: Pending Payment, Confirmed, Cooking, Ready for Pickup, In-Transit, and Delivered.
Chef & Kitchen Tracker
Active capacity indicators, menu configurations, sanitation checks log, and total daily earnings tracking for automated payouts.
Driver Fleet Live Map
Shows last known locations of drivers (updated when status changes are pushed), active routes, and pickup allocations.

WhatsApp Business API Deep Dive

To deploy a production-grade WhatsApp platform, we must utilize the Meta WhatsApp Business Cloud API. Standard consumer accounts or Web-automation scraping scripts are unstable, violate Meta TOS, and will result in sudden bans.

1. Direct Cloud API vs Aggregators

We analyze the optimal connection method for Homaatri's scale:

2. Step-by-Step Onboarding Process

  1. Meta Developer Portal Setup: Register an application as a "Business App" at developers.facebook.com. Add the "WhatsApp" product.
  2. Meta Business Manager: Create or link a Meta Business Suite account. Verify your business registration details (requires tax certificate or utility bills) to unlock high message volume tiers.
  3. Phone Number Linking: Add a dedicated phone number. The number must be capable of receiving a verification code via SMS or voice, and must NOT be linked to a standard user WhatsApp application.
  4. Generate System Token: Go to Business Settings -> System Users. Generate a permanent System Access Token with whatsapp_business_messaging and whatsapp_business_management scopes.
  5. Webhook Config: Register a webhook endpoint pointing to your backend (HTTPS). Subscribe to the messages field. Verify using a secret verification token.

Meta Policy & Sandbox Pitfalls: In Sandbox mode, you can only message verified tester numbers. Sandbox templates are approved automatically. In Production, you must submit templates for automated classification review by Meta. Reject rates increase if templates sound overly promotional under utility categories.

Backend Architecture & Stack

The backend requires robustness and low response times. We select Node.js (TypeScript) + Express or Python (FastAPI) running on Docker, using PostgreSQL for relational data and a lightweight queue for job buffering.

graph TD Internet[WhatsApp / Web Client] --> Nginx[Nginx Reverse Proxy & SSL] Nginx --> API[Node.js / Express API Service] API --> DB[(PostgreSQL Database)] API --> Queue[BullMQ Queue Manager] Queue --> Worker[Background Worker Process] Worker --> DB Worker --> LLM[LLM API Endpoint] Worker --> WABA[Meta WhatsApp Cloud API]

System Core Components

  • Express API: Lightweight HTTP server. Webhook path /webhooks/whatsapp acts as a high-speed ingestion sink.
  • BullMQ Queue: Queue library backed by PostgreSQL or a small Redis container. Captures raw WhatsApp message payloads. Protects backend from spikes during peak lunch/dinner ordering hours.
  • Cron Scheduler: Manages chef reminders (e.g. at 5:00 PM: "Confirm menu for dinner") and driver allocation routines.
  • Error Resilience: Implements Exponential Backoff retry schemes with Jitter on LLM API and Payment Gateway calls.

Database Schema Design

We use a relational structure (PostgreSQL) to ensure clean entity states and transactional integrity for order tallies, payments, and driver dispatch states.

Structured Order Extraction Code

Below is a production-ready Python/FastAPI implementation parsing WhatsApp messages to a validated JSON structure:

from typing import List, Optional
from pydantic import BaseModel, Field
import google.generativeai as genai
import json

# Define the target structure
class OrderItem(BaseModel):
    item_name: str = Field(description="Name of the food item, e.g. Roti, Chapati, Dal")
    quantity: int = Field(description="Number of portions requested")
    special_instructions: Optional[str] = Field(None, description="E.g. No spicy, extra ghee")

class StructuredOrder(BaseModel):
    items: List[OrderItem]
    delivery_time: Optional[str] = Field(None, description="Time mentioned for delivery, e.g., 8:00 PM")
    is_ambiguous: bool = Field(description="True if request is unclear or menu items don't match options")
    ambiguity_reason: Optional[str] = Field(None, description="Reason why the prompt is ambiguous")

def parse_order_text(user_message: str, active_menu_items: List[str]) -> StructuredOrder:
    genai.configure(api_key="GEMINI_API_KEY")
    
    prompt = f"""
    You are the order parser for Homaatri Kitchens.
    Extract the order details from the user's chat message.
    Cross reference food items with this list of active menu items for today: {active_menu_items}.
    If the user requests something not on the active menu, mark is_ambiguous as True.

    User Message: "{user_message}"
    """
    
    model = genai.GenerativeModel('gemini-1.5-flash')
    
    # Force structured output using Pydantic schema
    response = model.generate_content(
        prompt,
        generation_config=genai.GenerationConfig(
            response_mime_type="application/json",
            response_schema=StructuredOrder,
            temperature=0.1
        )
    )
    
    return StructuredOrder.model_validate_json(response.text)
// Node.js Express Webhook Endpoint for WhatsApp Cloud API
const express = require('express');
const crypto = require('crypto');
const app = express();
app.use(express.json());

const APP_SECRET = process.env.META_APP_SECRET;

// Webhook Verification (WhatsApp Configuration handshake)
app.get('/webhook', (req, res) => {
    const mode = req.query['hub.mode'];
    const token = req.query['hub.verify_token'];
    const challenge = req.query['hub.challenge'];

    if (mode && token) {
        if (mode === 'subscribe' && token === process.env.WEBHOOK_VERIFY_TOKEN) {
            console.log('Webhook Verified!');
            return res.status(200).send(challenge);
        }
        return res.sendStatus(403);
    }
});

// Post webhook event handler
app.post('/webhook', (req, res) => {
    // 1. Signature Verification for security
    const signature = req.headers['x-hub-signature-256'];
    if (!signature) return res.sendStatus(401);

    const hmac = crypto.createHmac('sha256', APP_SECRET);
    const digest = 'sha256=' + hmac.update(JSON.stringify(req.body)).digest('hex');
    
    if (signature !== digest) {
        console.warn('Invalid signature detected');
        return res.sendStatus(401);
    }

    // 2. Acknowledge immediately to avoid Meta message retries
    res.status(200).send('EVENT_RECEIVED');

    // 3. Offload work to Queue worker so we don't block Express thread
    const changes = req.body.entry?.[0]?.changes?.[0];
    if (changes && changes.field === 'messages') {
        const messageEvent = changes.value?.messages?.[0];
        if (messageEvent) {
            orderQueue.add('process-whatsapp-msg', { messageEvent });
        }
    }
});

Hostinger Linux VPS Deployment Strategy

Deployment on Hostinger uses a KVM 2 Linux VPS (Ubuntu 24.04). All backend components run inside isolated Docker containers managed by Docker Compose. Nginx acts as our secure gateway.

graph LR UserMsg[Client Message] -- HTTPS Port 443 --> Firewall[VPS Firewall UFW] Firewall --> Nginx[Nginx Reverse Proxy] Nginx -- Certbot SSL Certificates --> NodeAPI[NodeJS Docker Container] NodeAPI --> DBContainer[Postgres Docker Container] NodeAPI --> WorkerContainer[Worker Docker Container]

Auto Backups: Configure a cron job running daily on the host VPS. Execute docker exec -t postgres-db pg_dump -U postgres dbname and stream the output directly to a remote private S3 bucket or Google Drive folder using rclone. This safeguards customer records at zero additional cost.

Security Framework Guidelines

  • Webhook Integrity: Rejects all payloads that lack or fail the X-Hub-Signature-256 signature comparison.
  • API Rate Limiting: Enforce restriction layers at Nginx (max 15 requests per second per IP) to prevent DDoS attacks targetting our webhooks endpoint.
  • Database Port Lockdown: Block public access to PostgreSQL Port 5432 using UFW firewall rules on the host VPS. Allow connections strictly from localhost.

Scale & Interactive Cost Analysis

Building for Homaatri's scale means ignoring complex enterprise architectural paradigms. We avoid over-engineering by using the simplest system design possible.

What to Avoid (Over-engineered)
  • ❌ Kubernetes (K8s): Unnecessary server resources, complex networking, and maintenance fees.
  • ❌ Apache Kafka: Massively overkill for less than 1,000 requests/day. Simple DB queue is sufficient.
  • ❌ Microservices: Split codebases add network call latency, debugging overhead, and hosting costs. Keep a single backend service.
What to Use (Production-ready)
  • ✅ Monolithic Backend: Simple deployments, rapid coding speed, sharing types easily.
  • ✅ Docker Compose: Single command deployment, handles restart policies out-of-the-box.
  • ✅ Dockerized PostgreSQL Queue: Eliminates Redis if resources are constrained. Handles retries safely.
